# Версионные передачи NASFS

Ветка `feature/versioned-transfers` использует подписанный формат NASFS. Для новых хранилищ каталог SQLite и контейнеры создаются в приватном `StorageDir/.nasfs-versions`. Существующие хранилища продолжают открываться по прежнему пути. Файлы, ранее опубликованные прямо в `StorageDir`, остаются на месте. Сервер отвечает `Unsupported transfer format` на запросы прежнего формата. [Кодек](../common/src/version.c), [файловый сервис](../server/src/file_service.c), [хранилище](../server/src/version_store.c).

## PUT

Клиент разрешает имя в 128-битный ID и 256-битный дайджест текущей версии. Для нового имени клиент создаёт случайный ID и использует нулевой родительский дайджест. После открытия локального файла он отправляет размер, размер блока, профиль хеша, шифр и слот владельца вместе с ID и родителем. Клиент шифрует блоки ключом файла. Перед каждым блоком он передаёт защищённую строку индекса с номером, длиной шифротекста и хешем. Сервер один раз хеширует шифротекст блока, сверяет строку и сохраняет её вместе с шифротекстом. [Клиент](../client/src/client.c), [кодек](../common/src/version.c), [файловый сервис](../server/src/file_service.c).

Подпись Ed25519 покрывает дайджест канонического заголовка и корня индекса. Используются отдельные домены BLAKE2b-256 для индекса и манифеста. Дайджест манифеста служит идентификатором версии. Сервер проверяет размер и порядок всех записей, корень и подпись. После завершения всех записей он синхронизирует файл, связывает его с именем по дайджесту, синхронизирует каталог и коммитит индекс версий SQLite. Публикация проверяет текущего родителя в той же транзакции. Для двух конкурентных записей одного родителя подтверждение получает одна. [Файловая финализация](../server/src/file_service.c), [публикация](../server/src/version_store.c).

Хеш по умолчанию BLAKE2b-256, дополнительные профили SHA-256 и BLAKE3-256. Блоки поддерживаются от 4 КиБ до 4 МиБ, по умолчанию 64 КиБ. Управляющие кадры защищены XChaCha20-Poly1305 secretstream. Пароль владельца использует Argon2id для мастер-ключа. [Клиентские настройки](../client/src/main.c), [кодирование](../common/src/version.c).

## GET и очистка

`get` разрешает имя, затем запрашивает конкретные ID и версию. Команды `resolve <name>` и `get-version <id> <digest> <offset> <length|all> <local_file>` доступны также через `nasfs_client_run`. Для запроса диапазона сервер сначала передаёт полный индекс, затем только записи, пересекающие диапазон. Для полного GET индекс передаётся вместе с зашифрованными блоками. Сервер читает сохранённые строки индекса. Клиент проверяет подпись, ID, дайджест версии, хеши и теги блоков, затем корень индекса и полноту результата. Только после этого он публикует локальный файл через тот же защищённый staging. [API](../client/include/nasfs_client.h), [клиент](../client/src/client.c), [файловый сервис](../server/src/file_service.c).

`NASFS_EXPECTED_MANIFEST` задаёт ожидаемый дайджест из доверенного источника для GET по имени. Версии, заменённые более чем `VersionRetentionSeconds` назад, доступны для удаления через `collect`. По умолчанию период составляет 86400 секунд. Очистка проверяет AUTH и исключает версии, на которые указывает текущее имя. Уже открытый GET сохраняет читаемый fd после удаления версии из каталога. `VersionQuotaBytes` задаёт логический лимит объёма контейнеров и активных резервирований. При превышении лимита PUT получает явный отказ, после которого уполномоченный клиент может выполнить `collect`. Для каталога требуется локальный том с корректными блокировками SQLite. [Настройки](../server/src/config/config.c), [допуск и чтение](../server/src/file_service.c), [каталог и квота](../server/src/version_store.c).

## Восстановление ECC

`NASFS_ECC` на PUT выбирает `off`, `xor-4+1`, `xor-8+1`, `xor-16+1` или `rs-8+2`. По умолчанию `off`. Клиент рассчитывает чётность по шифротексту с тегами и дополняет последний неполный блок нулями для вычисления чётности. Профиль и строки индекса данных и чётности входят в подписанную версию.

При штатном GET сервер выдаёт индекс и пропускает тела записей чётности. Для ECC клиент подтверждает обработку блока перед чтением следующего. При несовпадении хеша он запрашивает группу с уже открытого fd, проверяет записи по подписанному индексу, восстанавливает блок и повторно проверяет хеш и файловый тег. Независимый источник свежести остаётся тем же. [ECC](../common/src/ecc.c), [клиент](../client/src/client.c), [сервер](../server/src/file_service.c).

## Возобновление

`put-resume <checkpoint> <local_file> <remote_name>` готовит приватный локальный журнал с точным подписанным шифротекстом. Повтор использует те же записи и версию родителя. Сервер связывает случайный токен с подтверждённой областью входа, именем, ID, заголовком и дайджестом. Публичный ключ входит в область для соответствующих способов AUTH. В моделях с общим паролем участники делят полномочия входа, поэтому защита попыток также опирается на приватность токена. Открытый staging с эксклюзивной блокировкой допускает одного писателя. [Клиент](../client/src/client.c), [сессия](../server/src/network/session.c), [журнал](../server/src/version_store.c).

Сервер останавливает приём новых записей при контрольной точке, дожидается завершения записей, синхронизирует файл и лишь затем обновляет позицию SQLite. Порог составляет 16 МиБ или 1 секунду. Частично записанный хвост при продолжении обрезается до сохранённой границы. Срок паузы и выдачи сохранённого результата задаёт `AttemptRetentionSeconds`, по умолчанию 86400. Публикация и запись успешного итога коммитятся одной транзакцией. Повтор после потери ответа может получить прежний итог без передачи блока. [Файловый сервис](../server/src/file_service.c), [каталог](../server/src/version_store.c).

`get-resume <checkpoint> <id> <digest> <local_file>` сохраняет проверенный шифротекст на клиенте. При повторе он запрашивает индекс и оставшийся диапазон той же версии, заново проверяет уже полученные записи и выпускает полный файл после итоговой сверки. Локальные журналы остаются для повторного запуска. Обычные PUT и GET работают без этих журналов. [Клиентский API](../client/include/nasfs_client.h), [клиент](../client/src/client.c).

## Границы следующих задач

Кэш должен ключевать проверенные диапазоны по серверу, области доступа, ID и дайджесту. Контекст файлового сервиса принимает субъект от AUTH. Текущие субъекты имеют общий набор полномочий, поэтому потребуется стабильный подтверждённый ID и ACL перед использованием в многопользовательской конфигурации. Метаданные контейнера подписаны вместе с текущим слотом владельца. Дополнительные слоты потребуют новой схемы выдачи ключей и проверки заголовка. FUSE должен вызывать тот же API. Для монтирования потребуются каталоги и атрибуты, а для записи правила `flush`, `fsync`, `rename` и `unlink`. [План](../REFACTOR_PLAN.md).

## Замер на целевом NAS

`tests/benchmark_target.py` запускается с отдельного клиента. NASFS и тестовый OpenSSH SFTP должны работать на одном NAS с выделенными cgroup v2. Для чтения `cpu.stat` используется отдельное управляющее SSH-подключение. OpenSSH проверяет закреплённый ключ хоста, а NASFS использует штатный pin. Сценарий сохраняет сырые измерения PUT и GET и сводку с p95, МиБ/с и CPU-секундами NAS на ГиБ.

`--series baseline` сравнивает NASFS с OpenSSH ChaCha20-Poly1305, AES-128/256-GCM и AES-256-CTR с отдельным MAC. Сценарий сверяет согласованные алгоритмы по журналу OpenSSH и сравнивает содержимое после GET. На вход SFTP подаётся заранее зашифрованный с той же длиной файл. SFTP делает `put -f` с последующим `rename` в выделенном каталоге. NASFS выполняет синхронизацию каталога и коммит метаданных. Гарантии при потере питания учитываются отдельно. `--series resume` и `--series ecc` измеряют отдельные профили NASFS. Подготовка локальных журналов входит в сквозное время resume. Используй отдельное хранилище NASFS для записей стенда. [Сценарий](../tests/benchmark_target.py).
