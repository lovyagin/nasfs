# История аудита NASFS

[Актуальный документ](../../AUDIT.md)

## История ревью до `bb68ed2`

Статусы, номера строк и результаты в этом разделе относятся к указанным срезам. Версии документов и исходников могли измениться после этих проверок.

### Ревью рабочей копии поверх `324c46b`

1. **[P1] Исправлено. Защита назначения GET.** Клиент проверяет тип и право записи, сравнивает назначение до и после получения данных и повторно сверяет запись перед заменой. Публикации NASFS в одном каталоге синхронизированы `flock`, а новое имя публикуется без перезаписи через `linkat`. Регрессии проверяют сохранность read-only файла, FIFO, симлинка и нового файла, подставленного во время передачи. Сторонний процесс, игнорирующий блокировку, всё ещё может изменить существующую запись между последней проверкой и `renameat`. POSIX не предоставляет атомарного сравнения inode при замене. [Публикация GET](../../client/src/main.c), [E2E](../../tests/test_end_to_end.sh), [тесты подмены](../../tests/test_transfer_recovery.py).
2. **[P2] Исправлено. Привязка staging GET к родительскому каталогу.** Родитель открывается до отправки GET. Временный файл создаётся с режимом 0600 через `openat`, а публикация и удаление работают относительно того же дескриптора. Проверяются перенос родителя, смена симлинка родителя и отмена через SIGTERM после переноса. Подставленный каталог не получает файл, а staging удаляется из исходного. [Восстановление GET](../../tests/test_transfer_recovery.py).
3. **[P2] Исправлено. Права журнала после ротации.** Демон наследует маску создания файлов. Все точки открытия журнала создают новый файл с режимом не шире 0644. Тест с унаследованным `umask 000` перемещает активный журнал и проверяет режим файла, созданного при следующем соединении. [Журнал](../../server/src/logging/log.c), [интеграция](../../tests/test_lifecycle.sh).
4. **[P2] Исправлено. Готовность демона в nasfsctl.** Сервер сообщает режим через тот же парсер, который использует при запуске. В daemon-режиме `nasfsctl start` ждёт статуса процесса запуска. Проверяются foreground, успешный запуск демона и, на Linux, ожидание дольше пяти секунд и SIGKILL после записи PID, пока готовность ещё не подтверждена. [Контрольный скрипт](../../utils/nasfsctl.in), [интеграция](../../tests/test_lifecycle.sh).
5. **[P2] Исправлено. Пути в поставляемом конфиге.** Общий шаблон заключает пути в двойные кавычки. Парсер сохраняет пробелы и `#` внутри кавычек, поддерживает экранирование кавычки и обратной косой черты, значения без кавычек и комментарии. Autotools создаёт каталоги журнала и PID с учётом пробелов, а шаблон systemd заключает в кавычки аргументы `ExecStart`. Обе сборки установлены в чистые префиксы с пробелами. В обеих прошли запуск и остановка через `nasfsctl`, вход по публичному ключу и побайтовый PUT/GET. Отдельно прошли запуск, перезапуск и передача через установленный CMake-юнит systemd в таком префиксе. [Парсер](../../server/src/config/config.c), [конфиг](../../server/config/nasfs.conf.in), [тест](../../tests/test_config.c).
6. **[P2] Исправлено. Совместимость keygen и читателей.** Общие пределы составляют 127 байт для имени алгоритма, 4096 для открытого ключа и 4999 для закрытого. Читатели принимают полные строки и отбрасывают остаток слишком длинной записи. На macOS liboqs вернул параметры `OV-Is`, клиент выдал диагностику о размере до создания файлов. Интеграции проверяют вход с ML-DSA. [Общие пределы](../../common/include/auth.h), [модульный тест](../../tests/test_auth.c).
7. **[P3] Исправлено. Подготовка SFTP GET в E2E-бенчмарке.** Подготовительный PUT обязан завершиться успешно до таймера. Скачанные байты сравниваются после снятия конечной отметки. На локальном OpenSSH проверен отказ записи поверх читаемого старого файла без GET, отметок времени и строки CSV. Контрольная подмена скачанных данных проверила отказ при несовпадении. Успешный замер дал ровно одну строку CSV. [Бенчмарк](../../tests/benchmark_e2e.sh).

На macOS и Ubuntu ARM64 CMake Release прошёл по 9 из 9 тестов CTest, Autotools на Ubuntu прошёл 8 из 8 `make check`, включая сетевые интеграции на loopback. ASan/UBSan прошёл полный CTest на macOS (9 из 9) и интеграции передачи и запуска на Ubuntu (2 из 2). Прошли `clang-format`, ShellCheck, `git diff --check` и локальный Linux clang-tidy с параметрами CI. Сетевые тома NFS/SMB и файловые системы без жёстких ссылок не проверялись.

### Ревью рабочей копии поверх `1417b0d`

1. **[P1] Исправлено. Обычный PUT через алиас.** На томах с заменой PUT и `mput` используют одну блокировку публикации. Обычный PUT проверяет байты имени записи каталога. На macOS для локальных томов, отличных от APFS, при наличии манифеста сервер сверяет запрошенное имя с его дайджестом. Это учитывает HFS+, который меняет нормализацию имени при записи. На APFS и HFS+ проверены отказ через алиас, GET исходного объекта с его манифестом и замена по исходному имени. На HFSX проверено хранение имён, отличающихся регистром. [Хранилище](../../server/src/storage.c), [регрессии PUT](../../tests/test_end_to_end.sh).
2. **[P1] Исправлено. Локальные коллизии `mget`.** Перед заменой клиент сопоставляет назначение с идентификаторами уже опубликованных файлов. Проверены алиасы через симлинк каталога, `..` и регистр. В последнем сценарии HFSX хранил два объекта с разными байтами, а APFS свёл их имена к одной записи. Батч завершился с диагностикой, и первый результат сохранился. [Публикация GET](../../client/src/main.c), [регрессии mget](../../tests/test_end_to_end.sh).
3. **[P2] Исправлено. Относительные пути в режиме демона.** Пути журнала, PID-файла и списка авторизованных ключей привязаны к исходному рабочему каталогу. Проверены создание журнала и PID-файла, вход по публичному ключу, PUT и GET в относительном `StorageDir`, а также удаление PID-файла при остановке. [Запуск](../../server/src/main.c), [интеграционный тест](../../tests/test_lifecycle.sh).
4. **[P2] Исправлено. Статус запуска демона.** Исходный процесс ждёт подтверждения после запуска слушателя и записи PID. При закрытии канала до ответа промежуточный процесс дожидается потомка и удаляет оставшийся PID-файл с идентификатором этого потомка, проверяя блокировку и идентичность записи. Проверены занятый порт, отказ создания PID-файла и штатный запуск. В Linux дополнительно проверен `SIGKILL` до слушателя и после записи PID, пока подтверждение ещё не отправлено. В обоих случаях исходный процесс вернул ошибку, а процесс демона и PID-файл отсутствовали. [Демон](../../server/src/utils/daemon.c), [PID-файл](../../server/src/utils/pid_file.c), [интеграционный тест](../../tests/test_lifecycle.sh).
5. **[P2] Исправлено. Длинные строки конфигурации.** Граница в 4096 байт проверяется до разбора директивы. Модульный тест считывает длинный `AuthPassword` на границе лимита в последней строке без перевода строки. Интеграционный тест проверяет отказ на более длинной строке, номер строки и отсутствие пароля в диагностике. [Парсер](../../server/src/config/config.c), [модульный тест](../../tests/test_config.c).
6. **[P2] Исправлено. Ошибка вычитания точек в PAKE.** Обе стороны возвращают ошибку до следующего скалярного умножения. Клиент закрывает соединение, а сервер отклоняет аутентификацию. В CMake и Autotools доступны модульные проверки отказа обеих сторон и успешного обмена. [PAKE](../../common/src/pake.c), [модульный тест](../../tests/test_pake.c).
7. **[P2] Исправлено. Ошибки команд SFTP.** Измеряемые PUT и GET и подготовка GET используют `sftp -b -`. На локальном OpenSSH успешный прогон дал шесть строк SFTP. Запрет чтения и записи на сервере прервал соответствующие операции без строки замера. Отдельная подстановка подтвердила передачу `-b -` и обработку кода 37 при отказе подготовительной загрузки. [Бенчмарк](../../tests/benchmark_blocksize.sh).
8. **[P3] Исправлено. Суммарная пропускная способность.** `combined` и `peak` используют `1 / (1/a + 1/b)`. Проверены восемь строк вывода, оба пика и результат 50 МБ/с для двух последовательных этапов по 100 МБ/с. [Оптимизатор](../../utils/nasfs_optimizer.c).

На macOS и Ubuntu ARM64 прошли CMake Release и CTest (9 из 9 на каждой системе) и Autotools `make check` (8 из 8 на каждой системе), включая сетевые интеграции на loopback. ASan/UBSan прошёл полный CTest на macOS (9 из 9) и целевые тесты запуска и PAKE на Linux. Проверки `clang-format`, ShellCheck, `git diff --check` и clang-tidy с параметрами CI на Linux прошли. На macOS clang-tidy сообщил о существующих знаковых битовых операциях и недоступности Linux-заголовка для тестовой библиотеки.

В этом проходе не проверялись реальная big-endian система, сетевые тома NFS и SMB и запуск установленного юнита systemd.

### Повторное ревью рабочей копии поверх `edd3e24`

- **[P2] Исправлено. CRC32 и Adler32 в сетевых метаданных кодируются в big-endian.** Обе стороны PUT и GET используют `crypto_engine_hash()`. Тест сверяет четыре байта каждой суммы в кадре метаданных. На little-endian macOS тест выявил обе ошибки до правки и прошёл после неё. GET вычисляет контрольные суммы заново из шифротекста. Контейнеры обеих сумм, записанные сборкой до исправления, прочитаны побайтово. Реальная big-endian система не проверялась. [Хеширование](../../common/src/crypto_engine.c#L330), [тест](../../tests/test_encryption.c#L179).
- **[P3] Исправлено. IOPS-бенчмарк разрешает относительный `NASFS_CLIENT_BIN` до запуска замеров.** С `--no-sftp --count 1 --runs 1` относительный и абсолютный пути дали по 16 замеров, включая по четыре пакетных GET. При принудительном отказе `mget` скрипт вернул код 37, вывел диагностику и пропустил строку CSV для сбойного замера. [Настройка бинарника](../../tests/benchmark_iops.sh#L29), [запуск `mget`](../../tests/benchmark_iops.sh#L196).

После исправления обоих замечаний на macOS Release прошли сборка, 9 из 9 тестов CTest, ShellCheck для IOPS и общего помощника, а также `git diff --check`.

До исправлений в повторном ревью на macOS Release также прошли 9 из 9 тестов CTest, ShellCheck для обоих бенчмарков и общего помощника, а также `git diff --check`. Короткие прогоны с `--no-sftp` дали 12 замеров block-size и 16 замеров IOPS с абсолютными путями. Реальная big-endian архитектура, Linux и SFTP в этом проходе не проверялись. Joern сообщил, что граф для текущих исходников отсутствует или устарел.

### Изменения после ревью `80a63a5`

- Клиент отклоняет HKDF и PBKDF2 для новых PUT и mput до загрузки соли и соединения. Для чтения проверяются подписанные NASLUKS-образцы обоих KDF, созданные клиентом `80a63a5`. Чтение старого неподписанного формата покрывает отдельный образец.
- Префикс и трейлер GET читаются асинхронно. Публикация PUT выполняется в рабочем потоке. При первоначальном переносе синхронными оставались серверные I/O заголовков. Следующая правка перенесла их и чтение слота в рабочий запрос открытия. Закрытие файлов вне публикации и удаление staging на путях отказа выполняются синхронно. Потеря ответа после публикации остаётся неизвестным исходом для клиента.
- Уборка при запуске ограничена файлами загрузки с ожидаемым именем, типом, владельцем и одной ссылкой. При активном сервере в том же каталоге уборка переносится на следующий запуск без конкурента. Перед обновлением нужно остановить старые экземпляры, которые не участвуют в блокировке.

### Рабочая копия поверх afc9d2a

- Серверная идентичность обязательна. Интеграционные тесты покрывают закреплённый ключ, несовпадение, ротацию и повреждение подписи или READY. При двух последних отказах тестовый прокси проверяет отсутствие AUTH/PAKE.
- Манифест покрывает имя, соль, алгоритмы, размер, NASLUKS-слот и упорядоченный шифротекст. GET открывает слот локальным мастер-ключом и сохраняет прежний файл при отказе. Опция ожидаемого манифеста позволяет проверить известную версию. Свежесть без доверенного эталона остаётся открытой.
- Сравнение гарантий с OpenSSH остаётся открытым. В NASFS видны наружные типы и размеры кадров. В SSH длина входит в зашифрованный пакет. Для NASFS ещё нужны независимый обзор рукопожатия, проверка повторов и смешения операций по полной матрице, пределы жизни ключей, аварийные испытания и измерения на целевом NAS. [RFC 4253](https://www.rfc-editor.org/rfc/rfc4253.html), [план](../../REFACTOR_PLAN.md).

### Состояние после рефакторинга

Проверенный срез `afc9d2a`, ветка `ref/api`. Ниже сохранён предыдущий аудит среза `3f8c96b`. Его выводы и номера строк относятся к тому срезу.

#### Что изменилось

- Сетевые тесты используют отдельные временные каталоги и порты, ждут готовности и завершают свой сервер по PID (`2cc18b0`).
- Закрытие сервера дожидается файловых открытий, чтений и записей сессии. Клиент откладывает закрытие источника до завершения локального чтения (`a9e2d84`).
- PUT открывает локальный источник до отправки запроса. GET пишет рядом с назначением во временный файл и публикует после проверок (`a83708a`).
- Сервер работает с плоскими именами относительно fd корня. PUT пишет во временный файл и публикует его через `renameat` после завершения записей и закрытия fd (`ee53806`, `a685c4b`).
- Текущий CLI ждёт `PUT_RESULT`, прежде чем сообщить об успехе или перейти к следующему файлу. Ранее опубликованные файлы пакета сохраняются при отказе следующего. Если ответ потерян, исход операции неизвестен. Публикация не включает синхронизацию файла и каталога с диском (`afc9d2a`). [Архитектура](../../ARCHITECTURE.md), [интеграционные тесты](../../tests/test_end_to_end.sh#L276).
- Выпущенных версий протокола пока нет. Суффикс `_V2` в двух командах и флаг `protocol_v2` обозначают ветку рукопожатия с итоговым ответом PUT. Общий кодек кадра используется в обеих ветках. По коду новый сервер принимает прежний HELLO, новый CLI требует READY с суффиксом. Матрица бинарников не проверялась. [Команды](../../common/include/protocol.h#L30), [диспетчер](../../server/src/network/session.c#L820), [клиент](../../client/src/main.c#L1342).

Создавать закрытый ключ сразу с режимом 0600 и проверять завершение записи. Проверить права при создании и сохранность старой цели при отказе. |

На macOS arm64 CMake Release и ASan/UBSan прошли по 8 из 8 тестов. Дополнительные прогоны с временными данными подтвердили обе ошибки читаемости. ### Цепочки и владельцы ресурсов

- **Соединение и AUTH, код.** CLI заполняет очередь, вызывает `uv_tcp_connect`, `on_connect` отправляет HELLO и регистрирует `on_read`. Серверный `main` регистрирует `session_on_new_connection` в `uv_listen`; после `uv_accept` сервер привязывает сессию к TCP handle и регистрирует `session_on_read`. Оба read callback удерживают неполный кадр между чтениями. `payload` ссылается на буфер до его сдвига, данные асинхронного PUT копируются. KEM устанавливает общий секрет, затем сервер проверяет AUTH либо PAKE. Парольный режим сверяет доказательство, привязанное к общему секрету сессии, режим ключа проверяет клиентскую подпись и allowlist, комбинированный — оба условия, PAKE — доказательство владения выведенным ключом. Только после положительной проверки он выставляет `is_authenticated`; состояние с именем AUTHENTICATED выставлено ещё при SECURE_READY. [CLI](../../client/src/main.c#L1449), [сервер](../../server/src/main.c#L105), [приём](../../server/src/network/session.c#L1213), [Проверка учётных данных](../../server/src/network/session.c#L173), [AUTH](../../server/src/network/session.c#L919).
- **PUT, код.** AUTH_ACK запускает PUT_REQ. Серверный `uv_fs_open` открывает конечный путь, callback пишет заголовок и отправляет PUT_ACK. Клиент только теперь открывает источник. Его `on_local_read` отправляет блок; callback сетевой записи запускает следующее локальное чтение. Сервер ставит запись с явным смещением, копией блока и указателем на сессию в контексте каждого запроса. PUT_DONE переводит сервер в состояние ожидания даже при незавершённых записях. Клиент использует завершение отправки PUT_DONE как сигнал перейти к следующему файлу или закрыться. [Клиент](../../client/src/main.c#L644), [открытие источника](../../client/src/main.c#L932), [серверная запись](../../server/src/network/session.c#L1090).
- **GET, код.** GET_REQ запускает серверное открытие, callback читает заголовок и отправляет GET_ACK. Клиент открывает назначение с усечением. Сервер читает через `do_get_next_chunk` → `on_get_fs_read`, успешное завершение отправки GET_DATA планирует следующее чтение. Клиент декодирует и синхронно пишет байты. GET_DONE завершает операцию и закрывает локальный fd через переход к следующему элементу. Размер проверяется только для ненулевого ожидаемого размера, итоги записи и закрытия полностью не сверяются. [Сервер](../../server/src/network/session.c#L584), [цепочка отправки](../../server/src/network/session.c#L1168), [клиент](../../client/src/main.c#L953).
- **Закрытие, код.** Сессия владеет TCP handle, receive-буфером, ключами и общим fd. `on_session_handle_closed` откладывает освобождение только по счётчику PUT-записей. Встроенный `fs_req` двух открытий и отдельный контекст GET-чтения также ссылаются на сессию. Клиентский GET пишет синхронно, а асинхронный PUT-read живёт отдельно от освобождаемого TCP handle. Передача fd и контекста до завершения всех callbacks требует общего правила владения. [Сервер](../../server/src/network/session.c#L394), [клиент](../../client/src/main.c#L631).

#### Уточнения к пунктам с наибольшим риском

- **T1/T4, код.** `uv_fs_write` может вернуть ошибку сразу, но сервер уже увеличил счётчик и игнорирует результат постановки. На этом пути callback, который должен уменьшить счётчик и освободить буфер, не будет вызван. В GET-ветке ошибка чтения возвращает состояние ожидания без закрытия fd. Повторное открытие может затереть его значение. Досрочное освобождение сессии, закрытие fd другого файла в пакете и точный порядок завершений под нагрузкой остаются гипотезами исполнения. Проверка после исправления — контролируемые ошибки постановки и завершения, остановка и отмена под ASan с учётом открытых fd и запросов. [PUT write](../../server/src/network/session.c#L1090), [GET read](../../server/src/network/session.c#L584).
- **T2/T3/T7, код и прошлый прогон.** Заголовок на диске имеет 26 байт: размер plaintext в порядке машины, 16 байт соли файла, по байту для шифра и хеша. Далее идут блоки с накладными байтами шифра без записанных границ. GET рассчитывает размер чтения из текущего BlockSize плюс 16 байт тега. Прошлый прогон 4096 → 65536 показал ошибку дешифрования; повторный штатный прогон выполнен с одинаковыми настройками. При неверном ключе ненулевой статус подтверждён, сохранность назначения после ошибки следует из порядка O_TRUNC и дешифрования в коде. Тест исправления должен начинаться с существующего назначения, проверять его хеш после ошибки и проверять чтение контрольных файлов каждого поддержанного формата. [Заголовок](../../server/src/network/session.c#L540), [чтение](../../server/src/network/session.c#L634), [назначение](../../client/src/main.c#L991).
- **P1/P2, высокая важность, код.** Общий parser проверяет верхнюю границу, но допускает нулевую длину тела. Клиентский SECURE_READY не проверяет точную длину заголовка и предыдущее состояние обмена перед вызовом libsodium. PUT_REQ и GET_REQ проверяют аутентификацию без требования свободного состояния и используют один встроенный `uv_fs_t`. ERROR имеет тип 0xFF, на клиенте расшифровывается только диапазон 0x10–0x1F. Пользователь может получить нечитаемое сообщение или нулевой выход при незавершённом обмене. Исправление проверить таблицей допустимых переходов и модульными негативными проверками общего кодека и декодеров команд. [Кодек](../../common/src/protocol.c#L22), [SECURE_READY](../../client/src/main.c#L876), [сервер](../../server/src/network/session.c#L941), [ERROR](../../common/include/protocol.h#L64).
- **P3, высокая важность, код.** В клиенте нет состояния доверия для адреса сервера, поэтому при первом и повторном подключении используется одинаковая процедура с новой временной KEM-парой. Проверка клиентской подписи на сервере решает другое направление аутентификации. Приёмка требует проверять доверие до AUTH и PAKE, включая отказ при смене ключа, и фиксировать отсутствие отправки учётных данных в тестах отказа. [Клиент](../../client/src/main.c#L820), [сервер](../../server/src/network/session.c#L749).
- **T6, высокая важность, код.** Путь собирается строкой и открывается обычным `uv_fs_open`. Для текущего плоского пространства имён достаточно удерживать fd каталога, строго валидировать один компонент, открывать его относительно fd с запретом ссылок и проверять тип объекта. Для будущих вложенных путей понадобится покомпонентный обход либо Linux `openat2` с ограничением разрешения. Отдельная проверка через `realpath` до открытия оставляет окно замены объекта. Проверка исправления — временное хранилище, ссылочные и неподдерживаемые объекты, контроль сохранности файлов. [Преобразование имени](../../server/src/network/session.c#L485), [открытие](../../server/src/network/session.c#L996).

Все запросы должны завершиться или отмениться до освобождения их контекста. |
| T5 | EOF, ошибка framing и ряд ошибок handshake закрывают клиент без явного признака незавершённой операции. Некоторые синхронные ошибки libuv и выделения памяти приводят к молчаливому выходу из callback. Отдельного дедлайна операции нет. [Приём](../../client/src/main.c#L812), [подключение](../../client/src/main.c#L1203), [отправка](../../client/src/main.c#L669). | Ненулевой код и понятная причина для каждого неуспешного запроса, включая отказ в соединении, разрыв и истечение срока ожидания. |
| T6 | Пути сворачиваются в basename и иногда подменяются запасным именем. Разные запросы могут попасть в один файл. Длинные имена режутся, результат `snprintf` не проверяется. Ограничение корнем хранилища не выражено в операции открытия файла и не учитывает ссылки. [Путь](../../server/src/network/session.c#L485), [PUT/GET](../../server/src/network/session.c#L996). | Ввести явный контракт имён и ошибок. Проверять расположение файла внутри корня на уровне хранилища. |
| T7 | Сервер сохраняет старые ветви чтения и записи без шифрования файла. Штатный клиент требует ключ, поэтому его политика и политика сервера различаются. GET принимает произвольный файл за шифрованный контейнер по одному размеру заголовка. [Клиент](../../client/src/main.c#L1328), [сервер](../../server/src/network/session.c#L653). | Серверная политика хранения проверяется независимо от CLI. У формата контейнера есть идентификатор, версия и проверяемая структура, а у старого формата — документированное правило чтения. |
| T8 | Пакет ограничен 512 элементами. CLI молча игнорирует хвост и допускает совпадающие базовые имена. Числовые переменные окружения парсятся без проверки конца строки. [CLI](../../client/src/main.c#L1310), [пакет](../../client/src/main.c#L1425). | Явная ошибка для лишних аргументов, неоднозначных имён и неверных чисел. Пакетный результат должен показывать, какие файлы действительно переданы. |

### Протокол, аккаунты и будущий драйвер

- **P1. Контракт протокола.** `protocol_pack_frame` принимает размер существенно больше лимита своего parser, допускает ненулевую длину с NULL и инициализирует только заголовок такого кадра. Parser допускает нулевую длину тела, хотя тип занимает один байт. Типы и размеры полезной нагрузки проверяются разрозненно в callback. Для заголовка используется сетевой порядок байтов, для `nasfs_block_meta_t`, размеров файлов и части данных на диске — порядок байтов машины. Требуются общий кодек и тесты именно этого кодека, включая частичные чтения и несколько кадров в одном буфере. [Кодек](../../common/src/protocol.c), [формат](../../common/include/protocol.h), [контейнер](../../server/src/network/session.c#L540).
- **P2. Состояние и ошибки.** Авторизация и состояние передачи проверяются несколькими независимыми флагами. PUT/GET меняют состояние и общий запрос открытия файла без явного допуска только из режима ожидания. `ERROR` отправляется и до handshake, и после него, а клиент до handshake его игнорирует и после handshake не расшифровывает. Нужны явные переходы, единый конверт ответа и коды ошибок, пригодные для клиента и драйвера. [Сервер](../../server/src/network/session.c#L710), [клиент](../../client/src/main.c#L812).
- **P3. Доверие и ключи.** Сервер генерирует временную KEM-пару на каждое подключение и отправляет открытый ключ без подписи. Клиент проверяет алгоритм и длину ключа, затем по SECURE_READY переходит к AUTH или PAKE. Постоянного ключа сервера, проверки отпечатка и хранилища доверенных серверов нет. ML-DSA в текущем протоколе используется для проверки подписи клиента на сервере. Шифрование канала само по себе не подтверждает личность удалённой стороны. Для рефакторинга зафиксировать проверку постоянного ключа сервера и подписи обмена до отправки AUTH или PAKE. Сценарии приёмки: заранее настроенный отпечаток, явное подтверждение при первом интерактивном подключении, отказ без настроенного доверия в пакетном режиме, повторный вход с тем же ключом, отказ при изменении ключа и явная процедура ротации. `AuthPassword` хранится в конфигурации как пароль. PAKE вызывается с обеих сторон, однако нет сетевого теста и в штатном конфиге метод отсутствует. Для ключей файла общий пароль плюс локальный `master.salt` и выбор KDF должны совпадать между клиентами. Соль и параметры master KDF не записываются в контейнер, ошибки сохранения соли не останавливают клиент. Потеря этой соли может сделать загруженные файлы нечитаемыми. Пустой файл отдельного доказательства правильности ключа не имеет. [Handshake клиента](../../client/src/main.c#L820), [KEM-пара сервера](../../server/src/network/session.c#L749), [master key](../../client/src/main.c#L1339), [PAKE](../../server/src/network/session.c#L859).
- **P4. Идентичность пользователя.** Сервер проверяет общий пароль и общий список ключей. Имя из запроса участвует в протокольных данных и логировании, но из него не получается постоянная серверная запись с UID/GID и группами. Хранилище общее. В локальных refs есть `origin/password-authentication` (`c480efd`, локальный CLI с файлом `users.txt` и ID) и `origin/key-authentication` (`b1e8116`, отдельный challenge-response API). Это заготовки для изучения интерфейсов, их интеграция с текущим протоколом не проверена. Оба refs содержат LICENSE. [Текущая проверка](../../server/src/network/session.c#L81).
- **P5. API для расширения.** CLI содержит глобальное состояние одного соединения, серверный dispatcher одновременно декодирует запросы, проверяет учётные данные и управляет диском. `nasfs_common` даёт низкоуровневые функции сборки и криптографии, но операции ФС как библиотечный интерфейс отсутствуют. Для следующего этапа нужны границы между состоянием соединения, аутентифицированным контекстом, файловым сервисом и CLI. На уровне протокола нужны версия/возможности, типизированный статус и способ отличить ответ на запрос от серверного события. В текущем CLI можно сохранить последовательную обработку. [Клиент](../../client/src/main.c), [сервер](../../server/src/network/session.c), [сборка](../../CMakeLists.txt).
- **P6. ACL.** В текущих исходниках ACL отсутствует. Из заметки научника для контракта нужны стабильный идентификатор объекта, проверка на сервере по установленной личности и возможность запросить права. Способ хранения прав (B-дерево, MurmurHash, ACL1) можно выбирать отдельно. На доступной странице `permissions` не удалось подтвердить лицензию и указанный в заметке путь `linux_permissions_repo`. До подтверждения происхождения и лицензии достаточно описать границу API. [Репозиторий permissions](https://github.com/Alec-afana/permissions).
- **P7. Кеш и офлайн.** Сейчас у файла нет версии, у клиента нет подписок, сервер не может адресно сообщать об изменениях. Требования для следующего этапа: уметь передавать событие инвалидации, версию объекта и признак конфликта, после переподключения сверять версии и понимать, были ли пропущены события. Размер логического блока кеша следует отделить от размера сетевого чанка и границ шифротекста. Для офлайна отдельно определить TTL чтения, что делать с записью и как повторять операцию с базовой версией. Нельзя считать сохранёнными данные, которые существовали только в DIRTY-кеше. 2Q, лимиты наблюдателей, WAL и полный ACL остаются предметом требований. Лицензию и содержимое архива кеша при проверке подтвердить не удалось. [Репозиторий ВКР](https://github.com/Alec-afana/vkr).

- **P8. Создание ключей.** Частный ключ создаётся через обычный fopen и получает режим 0600 после записи. Результаты закрытия и chmod игнорируются. Совпадающие входные пути приводят к тому, что запись открытого ключа заменяет только что записанный закрытый. Проверить создание с закрытым режимом с самого начала, независимость путей и отказ второй записи. [keygen](../../client/src/main.c#L187).

### Эксплуатация, тесты и измерения

- **E1. Конфиг.** Сервер без аргумента ищет `config/nasfs.conf` относительно текущего каталога, в рабочем дереве файл лежит в `server/config`. Поставляемый конфиг слушает на 5252, клиент по умолчанию обращается к 8080. Невалидный явный конфиг заменяется набором defaults, а частично выделенные строки при этом теряются. `ClientTimeout` загружается, но не применяется. `MaxConn` передаётся как backlog для `uv_listen`, поэтому активные сессии им не ограничиваются. Ошибки преобразования bind-адреса и `uv_tcp_bind` игнорируются. `StorageDir` из поставляемого конфига установка не создаёт. [Запуск](../../server/src/main.c#L52), [парсер](../../server/src/config/config.c#L45), конфиг (`server/config/nasfs.conf` на историческом срезе).
- **E2. Парсер.** В `trim_string` движение указателя по ведущим пробелам не сдвигает содержимое строки. В обработке пустой/пробельной строки проверка конца может уйти за её начало. Файл читается кусками по 512 байт без диагностики длинных строк. Неизвестные ключи и часть ошибочных значений молча принимаются. Проверить пустые/длинные строки, ошибки чтения, диапазон порта и повторяющиеся параметры. [Конфиг](../../server/src/config/config.c#L54), [trim](../../server/src/config/config.c#L252).
- **E3. Служба.** Unit рассчитан на forking и не задаёт системного пользователя. `nasfsctl` может выбирать PID через общий поиск процесса, а пути конфига, лога и PID-файла заданы независимо от действительных настроек сервера. `SIGTERM` останавливает цикл, затем сервер закрывает слушатель и сигнал-хендлеры, делает один неблокирующий проход и игнорирует результат `uv_loop_close`. Проверить startup и shutdown с активной передачей, устаревший PID и установку под целевым префиксом. [Служба](../../systemd/nasfs.service.in), [управление](../../utils/nasfsctl.in), [остановка](../../server/src/main.c#L120).
- **E4. Реальные проверки и заглушка.** E2E проверяет хеш скачанного файла, варианты KEM и способы password/publickey/оба. Тест шифрования проверяет round-trip и отрицательный код с неверным ключом, но иной хеш сохранённого файла сам по себе не доказывает шифрование и тест не проверяет сохранность прежнего локального файла. `test_request_payload_parsing_backward_compatibility` в `test_encryption.c` тестирует собственную копию старого алгоритма с 24-байтовой солью. Боевой PUT использует 16 байт соли, размер и идентификаторы алгоритмов. [E2E](../../tests/test_end_to_end.sh), [шифрование](../../tests/test_file_encryption.sh), [заглушка](../../tests/test_encryption.c#L178), [PUT codec](../../client/src/main.c#L544).
- **E5. Изоляция тестов.** Оба сетевых теста используют порт 8080, глобальный `pkill`, фиксированные паузы вместо ожидания готовности, рабочие данные могут пересекаться при параллельном `make check`. Тесты полагаются на каталог пользователя для соли. Нет общего таймаута запуска/сценария. Для нового набора нужны свой порт и временные данные на каждый сценарий, остановка только созданного дочернего процесса, логи при ошибке и запуск параллельно. [CMake](../../CMakeLists.txt), [Autotools](../../tests/Makefile.am), [E2E cleanup](../../tests/test_end_to_end.sh#L121).
- **E6. Паритет сборок и CI.** CMake регистрирует ECC и PAKE, Autotools их не запускает, ECC там даже не компилируется. `common/Makefile.am` не передаёт include-флаги libsodium/OpenSSL, а тестовые цели используют только include каталоги проекта. CI использует общий плавающий образ `latest`, сборка образа на push ограничена `main`, а install smoke проверяет наличие файлов. Следует сохранить проверки форматирования, clang-tidy, обеих сборок и ASan/UBSan, а прохождение Linux подтвердить отдельно. [CMake](../../CMakeLists.txt), [common](../../common/Makefile.am), [тесты](../../tests/Makefile.am), [CI](../../.github/workflows/ci.yml), [образ](../../.github/workflows/build-ci-image.yml).
- **E7. Висячие компоненты.** ECC — XOR-паритет с модульным тестом и вызовами в `benchmark`; вызовов из клиента, сервера и оптимизатора нет. `nasfs_optimizer` собирается CMake и печатает рекомендации, в install отсутствует и конфиг автоматически не меняет. Обе вещи надо явно считать экспериментами либо дать им рабочий сценарий и проверку. [ECC](../../common/src/ecc.c), [оптимизатор](../../utils/nasfs_optimizer.c), [цели](../../CMakeLists.txt).
- **E8. Бенчмарки.** Прогоны сравнений с SFTP здесь не выполнялись. В скриптах есть зависимости от GNU `date +%s%N` и локального SSH. В IOPS для batch PUT создаются ссылки с уникальными именами на один исходник, а SFTP записывает отдельные файлы. В batch GET проверяется код команды, но нет сверки содержимого каждого файла. Сравнение требует одинаковых условий, проверки результатов и учёта стоимости открытия сессии. Оптимизатор измеряет вычисления в памяти, поэтому его рекомендации требуют проверки на переносе реальных файлов. [IOPS](../../tests/benchmark_iops.sh#L167), [блоки](../../tests/benchmark_blocksize.sh), [E2E](../../tests/benchmark_e2e.sh), [оптимизатор](../../utils/nasfs_optimizer.c).

- **E9. Журналирование.** Файл лога открывается синхронно при каждой записи из event loop. В daemon mode при недоступности файла вывод может уйти в перенаправленный stdout. Нужен проверяемый результат инициализации журнала и понятное поведение при недоступности файла. [Лог](../../server/src/logging/log.c), [daemon](../../server/src/utils/daemon.c).

Порядок исправлений и решения о совместимости вынесены в [REFACTOR_PLAN.md](../../REFACTOR_PLAN.md).
